# Phase 06: Asset Lifecycle Fast Track

## Goal

Fix the HIGH/MEDIUM asset gaps in one fast batch: return flow consolidated into bast-service (kills racy `BAST-RTN-0001` numbering), asset PATCH becomes strict allow-list (status no longer directly editable), DELETE creates a BAST DISPOSAL draft instead of silently disposing, and the create dialog gains location/serialNumber/specification/condition fields with the edit dialog dropping the status selector.

**Mode**: mvp

## Requirements

- Gap 1 (HIGH): `app/api/assets/[id]/return/route.ts` — remove manual BAST creation + legacy `BAST-RTN-0001` numbering; call `createBastService` from `lib/services/bast-service.ts` with `BastType.RETURN` (atomic counter numbering + transition table apply on later approval)
- Gap 2 (HIGH): `app/api/assets/[id]/route.ts` PATCH — strict zod allow-list (like SEC-08 for BAST); `status` removed from accepted body (lifecycle-governed only); `condition` stays editable; unknown keys → 400
- Gap 3 (HIGH): `DELETE /api/assets/[id]` — create a BAST DISPOSAL draft via `createBastService` (type DISPOSAL) instead of silently setting DISPOSED; asset record stays until the draft is approved
- Gap 4 (MEDIUM): `components/create-asset-dialog.tsx` — add Location (from `locations` prop — note: the dialog currently receives only `categories`; caller `assets/page.tsx` already fetches `locations` and passes to AssetsTable, so thread it through), Serial Number, Specification, Condition fields; preserve existing dialog layout pattern exactly
- Gap 5 (MEDIUM): `components/edit-asset-dialog.tsx` — REMOVE the status `<Select>` (status is lifecycle-governed now); keep condition select + all other fields

## Success Criteria (must be TRUE)

1. POST /api/assets/[id]/return creates a RETURN BAST draft whose number follows `BAST/YYYY/MM/NNNN` (atomic counter), not `BAST-RTN-*`.
2. PATCH /api/assets/[id] rejects `status` and unknown keys (400); accepts only allow-listed fields; condition remains editable.
3. DELETE /api/assets/[id] creates a DISPOSAL BAST draft and does NOT change asset status; approval of that draft later runs the DISPOSAL transition (DISPOSED + holder null).
4. Create dialog offers Location, Serial Number, Specification, Condition; edit dialog no longer offers Status.
5. `npm run build` + `npx tsc --noEmit` pass; no new `any`.

- `lib/services/bast-service.ts` — `createBastService` input shape (CreateBastInput), actor type, BastType handling; the service already handles RETURN/DISPOSAL in its transition table
- `app/api/assets/[id]/return/route.ts` — current manual BAST creation to be replaced (read full: it sets recipientName=holder, targetLocationId=asset.locationId, creatorId=user.userId, status DRAFT)

## Task 1 — Return route → bast-service (Gap 1)

Rewrite `app/api/assets/[id]/return/route.ts` POST:

1. Keep: `requireRole(UserRole.STAFF_ASSET)` gate; asset existence check; `if (asset.status !== "IN_USE") return errorResponse("Asset is not currently in use", 400)`.
2. Replace the entire `$transaction` block with a call to `createBastService`:

```ts
const result = await createBastService(
  {
    type: BastType.RETURN,
    description: `Pengembalian otomatis aset: ${asset.name}`,
    effectiveDate: new Date().toISOString(),
    recipientName: asset.holder?.fullName || "Previous Holder",
    recipientPosition: "Employee",
    items: [
      {
        assetId: asset.id,
        conditionBefore: asset.condition,
        targetLocationId: asset.locationId,
      },
    ],
  },
  { userId: user.userId, fullName: user.fullName, role: user.role }
);
```

3. Keep the response shape: `successResponse(result, "BAST Return draft created successfully. Please review and approve.")` — result is the created bast (service returns it; if the service returns `{ data }` or the bast directly, adapt).
4. Delete the now-unused imports (`prisma` if unused elsewhere in the file, `BastType` only if unused — actually BastType is still used for the call; keep as needed). Lint-clean the file.
