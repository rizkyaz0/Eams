# Phase 02: BAST Consolidation & Authorization Rollout

## Goal

All BAST business logic lives in one typed service with legal transitions per BastType and separation of duties, and every mutating endpoint/server action (assets, bast, maintenance, categories, locations, divisions) enforces roles through a single `requireUser()`/`requireRole()` choke point with generic error responses. This phase kills the largest HIGH finding (missing role checks) and the behavioral divergence between REST and server-action BAST paths.

**Mode**: mvp

## Requirements

- SEC-06: `requireUser()` (401) dan `requireRole(min)` (403) di `lib/security.ts` sebagai satu titik penegakan
- SEC-07: Semua endpoint mutasi (assets, bast, maintenance, categories, locations, divisions) + server actions memanggil `requireRole()` sesuai role matrix
- SEC-08: `PATCH /api/bast/[id]` tidak lagi menyebar body mentah (`{ ...body }`) — hanya field allow-list via zod `.strict()`
- SEC-09: Respons error generik — tidak membocorkan `error.message` internal ke klien
- BUG-02: Logika BAST dikonsolidasi ke satu `lib/services/bast-service.ts` — REST handlers + server actions menjadi thin adapters; transisi per `BastType` bertipe
- BUG-04: Separation of duties — creator tidak bisa approve BAST sendiri
- BUG-05: `approverId`/`approverName` tercatat benar saat approval (pakai `user.userId`)
- TEST-03: Unit test RBAC matrix (DEFERRED — no vitest infra; developer rejected install in Phase 1)
- TEST-04: Test BAST workflow (DEFERRED — same)

## Success Criteria (must be TRUE)

1. Every mutating endpoint and server action returns 401 for anonymous callers and 403 for callers below the required role — no mutation is reachable without authorization.
2. BAST create/approve/reject via REST and via server actions produce identical outcomes through the same service, with `approverId`/`approverName` recorded from the authenticated actor (`user.userId`).
3. The creator of a BAST is rejected when attempting to approve or reject their own BAST (separation of duties), regardless of their role.
4. `PATCH /api/bast/[id]` accepts only allow-listed fields via a strict zod schema; attempts to set `status`, `bastNumber`, or other non-editable fields are rejected instead of silently applied.
5. Error responses returned to clients are generic — internal `error.message` content never leaks.

## Task 1 — lib/security.ts choke point (SEC-06)

Create `lib/security.ts` (server-only, like lib/auth.ts):

```ts
// lib/security.ts
import { getCurrentUser, hasMinimumRole } from "@/lib/auth";
import { UserRole } from "@prisma/client";
import { unauthorizedResponse, forbiddenResponse } from "@/lib/api-response";

/**
 * Require an authenticated user; returns unauthorizedResponse() when absent.
 */
export async function requireUser() {
  const user = await getCurrentUser();
  if (!user) return unauthorizedResponse();
  return user;
}

/**
 * Require an authenticated user at or above minimumRole; returns
 * forbiddenResponse() when below. Single choke point for SEC-07.
 */
export async function requireRole(minimumRole: UserRole) {
  const user = await getCurrentUser();
  if (!user) return unauthorizedResponse();
  if (!hasMinimumRole(user.role, minimumRole)) {
    return forbiddenResponse("Insufficient role");
  }
  return user;
}
```

Type: return `NextResponse | JWTPayload` union is awkward; instead return `JWTPayload | null` PLUS export `isErrorResponse`... NO — keep it simple and match repo patterns: return the user when authorized, and return the response object when not. Route handlers do `const user = await requireRole(UserRole.STAFF_ASSET); if (!("userId" in user)) return user;`. Alternative (cleaner, avoids `in` checks): return type `{ user: JWTPayload | null; response: NextResponse | null }`. Decide in implementation — must be uniform across all call sites and ergonomic. Commit after creating + one proof call site (users route).

## Task 4 — BAST service consolidation (BUG-02)

Create `lib/services/bast-service.ts` (server-only, imports db + auth). Move create/approve/reject business logic here as pure typed functions receiving the actor:


**Transitions per BastType (typed switch — the legal transition table from ROADMAP research flag):**

| BastType | On approve: asset status | On approve: holder/location |
|---|---|---|
| ASSIGNMENT | IN_USE | holderId=targetHolderId; locationId=targetLocationId |
| PROCUREMENT | IN_USE | holderId=targetHolderId; locationId=targetLocationId |
| RETURN | AVAILABLE | holderId=null; locationId=targetLocationId |
| MUTATION | keep status (IN_USE if conditionBefore truthy else AVAILABLE per REST; choose server-action semantics: status unchanged — document choice in code comment) | locationId=targetLocationId |
| MAINTENANCE_OUT | IN_MAINTENANCE | — (REST auto-creates Maintenance ticket; keep that behavior) |
| MAINTENANCE_IN | AVAILABLE | — |
| DISPOSAL | DISPOSED | holderId=null |

**Divergence to resolve (write a code comment citing this table):**
- REST `approve/route.ts` sets status based on `conditionBefore` truthiness for MUTATION; server action keeps status. Pick: MUTATION preserves current status unless targetLocationId present (document).
- REST sets `updateData.condition = detail.conditionAfter` always; server action too — keep.
- REST approve creates Maintenance ticket on MAINTENANCE_OUT; server action does NOT — keep the REST behavior (it's the richer one), document.
- REST approve does NOT check separation of duties — server action neither — both get Task 5.

Create/approve/reject implement the shared transition table; then:
- `lib/actions/bast-actions.ts` → thin adapters calling the service with `assertUser()`-derived actor (keep `{ success, data }`/`{ success, error }` envelope + revalidatePath + "use server")
- `app/api/bast/route.ts` POST → thin adapter (parse body, call service, respond successResponse 201)
- `app/api/bast/[id]/approve/route.ts` + `reject/route.ts` → thin adapters
- `app/api/bast/[id]/route.ts` PATCH → REMOVE approve/reject embedded logic; keep only editable-field updates (see Task 6); DELETE stays
